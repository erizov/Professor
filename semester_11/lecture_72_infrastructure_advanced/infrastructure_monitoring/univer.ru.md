# Infrastructure Мониторинг

**Алгоритм:** infrastructure_monitoring  
**Дисциплина:** Monitoring & Security

## Определение алгоритма

Infrastructure Мониторинг — это процесс непрерывного сбора, анализа и оценки метрик
системы или приложения в реальном времени с целью обнаружения проблем, аномалий и обеспечения
производительности и надёжности системы.

## Техническое описание

### Что делает алгоритм

Infrastructure Мониторинг — это процесс непрерывного сбора, анализа и оценки метрик
системы или приложения в реальном времени. Алгоритм отслеживает ключевые показатели производительности
(KPI), сравнивает их с установленными порогами и генерирует события при обнаружении аномалий или
нарушений.

**Основные этапы:**
1. Сбор метрик из различных источников (логи, сенсоры, API)
2. Агрегация и нормализация метрик
3. Сравнение текущих значений с пороговыми (thresholds)
4. Обнаружение аномалий через статистические методы или ML
5. Генерация алертов и уведомлений
6. Хранение истории метрик для анализа трендов

**Ключевые структуры данных:**
- Time-series базы данных для хранения метрик
- Окна скользящих средних (rolling windows)
- Графы зависимостей между метриками
- Очереди событий для обработки алертов

**Временная сложность:** O(m × n), где m — число метрик, n — частота проверки

**Пространственная сложность:** O(m × h), где h — глубина истории

**Сильные стороны:**
- Раннее обнаружение проблем
- Автоматизация реагирования на инциденты
- Исторический анализ и прогнозирование
- Масштабируемость для больших систем

**Слабые стороны:**
- Риск ложных срабатываний (false positives)
- Высокое потребление ресурсов при большом количестве метрик
- Сложность настройки порогов
- Зависимость от качества исходных данных

**Типичные ошибки:**
- Установка слишком чувствительных порогов → alert fatigue
- Отсутствие корреляции между связанными метриками
- Игнорирование временных паттернов (day/night, weekdays/weekends)
- Недостаточное логирование контекста при генерации алертов

## Применение в Monitoring & Security

1. Мониторинг производительности веб-приложения: отслеживание метрик response time (p50, p95, p99), throughput (RPS), error rate с порогами 200ms/500ms/1000ms и генерацией алертов при превышении
2. Обнаружение аномалий в сетевом трафике: анализ пакетов в реальном времени для выявления DDoS-атак, сканирования портов, необычных паттернов соединений
3. Мониторинг состояния Kubernetes-кластера: сбор метрик CPU, памяти, дискового I/O для каждого пода с агрегацией на уровне нод и автоматическим масштабированием

## Пример сценария по шагам

**Входные данные:**
Метрики веб-сервера за последнюю минуту:
- CPU usage: 85%
- Memory usage: 78%
- Request rate: 1200 req/s
- Error rate: 2.5%
- Response time (p95): 450ms

Пороги (thresholds):
- CPU: 80%
- Memory: 75%
- Request rate: 1000 req/s
- Error rate: 1%
- Response time: 300ms

**Шаг 1: Сбор метрик**
Собираем текущие значения из системы мониторинга (Prometheus, Datadog)

**Шаг 2: Сравнение с порогами**
- CPU: 85% > 80% → ПРЕВЫШЕН
- Memory: 78% > 75% → ПРЕВЫШЕН
- Request rate: 1200 > 1000 → ПРЕВЫШЕН
- Error rate: 2.5% > 1% → ПРЕВЫШЕН
- Response time: 450ms > 300ms → ПРЕВЫШЕН

**Шаг 3: Анализ корреляции**
Все метрики превышены одновременно → возможна атака или пиковая нагрузка

**Шаг 4: Генерация алерта**
Создаётся критический алерт с приоритетом HIGH:
- Тип: Performance degradation
- Время: 2024-01-15 14:32:00
- Метрики: CPU, Memory, Request rate, Error rate, Response time
- Рекомендация: Проверить нагрузку, возможен DDoS

**Шаг 5: Действия**
- Отправка уведомления в Slack/PagerDuty
- Автоматическое масштабирование (если настроено)
- Логирование события для последующего анализа

**Итоговый результат:**
Обнаружена критическая ситуация, система автоматически реагирует на проблему

## Вопросы для самопроверки

### Базовый уровень

1. Какие метрики являются наиболее критичными для мониторинга веб-приложения? Обоснуйте выбор с точки зрения влияния на пользовательский опыт.
2. Объясните разницу между метриками и логами. Когда следует использовать каждый подход для мониторинга системы?

### Средний уровень

1. Как избежать проблемы 'alert fatigue' при настройке порогов мониторинга? Предложите стратегию динамической настройки порогов на основе исторических данных.
2. Опишите алгоритм корреляции между метриками. Как определить, что несколько превышений порогов связаны одной причиной, а не являются независимыми событиями?

### Продвинутый уровень

1. Как применить машинное обучение для автоматического обнаружения аномалий в метриках? Сравните подходы: статистические методы (z-score, IQR) vs ML (Isolation Forest, LSTM).
2. Разработайте архитектуру системы мониторинга для распределённой системы с тысячами сервисов. Как обеспечить масштабируемость и низкую латентность?

## Практические задания

### Уровень 1 — базовый

Реализуйте простую систему мониторинга метрик. Создайте класс, который:
- Хранит метрики (CPU, memory, request rate) с временными метками
- Сравнивает текущие значения с порогами
- Генерирует события при превышении порогов
Протестируйте на синтетических данных с различными сценариями.

### Уровень 2 — прикладной

Разработайте систему мониторинга для веб-приложения. Используйте реальные
метрики (можно использовать Prometheus или создать симулятор). Реализуйте:
- Сбор метрик из нескольких источников
- Агрегацию метрик (средние, процентили)
- Обнаружение аномалий (статистические методы или простой ML)
- Генерацию алертов с приоритетами
- Хранение истории метрик
- Визуализацию на графиках

### Уровень 3 — исследовательский

Создайте исследовательскую систему мониторинга с применением машинного
обучения. Сравните различные подходы:
- Классические статистические методы (z-score, moving average)
- ML-методы (Isolation Forest, LSTM для временных рядов)
- Гибридные подходы
Оцените качество обнаружения аномалий (precision, recall, F1-score) на реальных или синтетических
данных. Проанализируйте ложные срабатывания и пропущенные аномалии.
